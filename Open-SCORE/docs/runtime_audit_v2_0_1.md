# v2.0.1 运行检查：保存故障、CPU/GPU 与策略行为

2026-09-06，本机 i7-14700KF（20 核、28 线程）、32 GB 内存、RTX 5070 Ti 16 GB，PyTorch 2.13.0+cu130。

## 保存故障与恢复

`train_20260906_rule` 在替换 `latest.tmp -> latest.pt` 时收到 WinError 5。日志没有 CUDA OOM 或非有限 PPO 损失；哪个外部程序占用文件尚未确定。父调度器随后按失败清理逻辑停止其余子进程。

`storage.replace_file` 对 Windows 5/32/33 错误最多尝试 9 次，总退避 4.55 秒，始终保留旧文件，其他异常直接上报。5 个新增测试覆盖临时锁、持续锁和其他错误，包含 checkpoint 与 JSON；全套 81 项通过。

对 `outputs/v2_parallel_100k_w3_new` 的 23 个 latest/固定预算检查点进行限定源码版本的兼容迁移。原始文件及 manifest 位于该目录 `recovery/windows_checkpoint_io`。模型参数、优化器、随机状态、计数器、配置逐项经重新加载核对不变；旧来源另保存在 checkpoint 历史字段。仅源码保存函数变化，训练算法与配置没有变化。

恢复时已有三个 100,000 步模型；其余为 79,596、26,521、25,000 步。从已有进度按原来三个并发任务继续，不重新训练已完成的节点。恢复从新回合开始，遵循已有断点语义。

## 超参数和 GPU 测速

128 维、2 层、4 头来自根目录 v2 研究方案的第一版建议，模型约 493,573 参数。batch 16、rollout 64 个上层事件是初始实现配置，没有完成超参数优选。每次优化对 16 个事件逐个前向后合并损失，尚未实现跨事件批量编码与解码；改变 batch 也会改变优化器步数，不能把吞吐测速当作公平的学习效果比较。

主算法混合 8v8/12v12，固定 50 步局长，单进程单 CPU 线程，约 1,024 物理步的顺序短测如下。运行前另做了约 256 步初测，两次方向一致。CUDA 调用可成功运行，记录了同步完成后的耗时；不同设备和 batch 的数值轨迹并不相同。

| 上层 / 下层设备 | batch 16 物理步/秒 | batch 64 物理步/秒 |
| --- | ---: | ---: |
| CPU / CPU | 63.2 | 59.9 |
| CUDA / CPU | 43.4 | 28.1 |
| CUDA / CUDA | 48.4 | 25.1 |

以上使用 `train` 记录的采样、更新、保存吞吐，完整调用速度另存原始 JSON。当前实现直接迁移 GPU 没有提速；这不证明经过批量化的实现、较大规模或更大网络不适合 GPU。原始记录和测试汇总见 `outputs/v2_validation/parallel_runner/verification.json`。可用 `scripts/benchmark_training_devices.py` 在新输出目录重测。

真正发挥 GPU 的后续方向是把多个环境和事件组成带掩码的批次、批量编码，以及减少自回归小算子和 CPU/GPU 同步。再通过统一预算实验评估更大的 rollout、minibatch 和网络容量。此次恢复没有中途改变这些参数。

## 大规模与后备队行为的限制

共享实体编码器和自回归分组头允许变长输入，参数量不按人数增长；注意力和解码的计算量仍随规模增长。用同一个已训练模型，在 16v16、32v32、64v64 各完成一次合法初始动作和环境宏观转移，只能证明接口能处理这些形状，不能证明策略效果或收敛。

这些贪心动作全部选择后备队，不能用其较低耗时说明复杂大规模分组高效。进一步对训练种子 20260905、100,000 步的主算法进行随机动作抽样：在 8v8、12v12、16v16 各 10 个独立诊断开局，共 30 个开局全部进入后备队。相同检查中的规则释放模型没有把成员放入后备队。诊断记录保存在运行目录 `recovery/windows_checkpoint_io/initial_action_probe.json`。

该观察是一个训练种子的开局行为，不是完整回合胜率或所有种子的结论。后备队执行独立导航规则，因此需要检查最终胜率与完整轨迹，排除算法主要依赖后备队规则、没有学到有意义分组的可能。不能仅凭能运行、参数更新或开局合法就宣称方法有效。应在本轮配对结果基础上再判断探索不足、稀疏终局奖励、后备队动作设计和冻结执行器能力的影响。
