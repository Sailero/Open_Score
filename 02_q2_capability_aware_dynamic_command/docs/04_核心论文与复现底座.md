# 核心论文与复现底座

## 1. 结论

最稳妥的工程策略不是押注一个仓库完成全部工作，而是分三层：

1. **科学骨架和强 baseline：ALMA**；
2. **快速验证：当前 SwarmBattle / MultiFront-AD clean-room 场景**；
3. **高吞吐与外部有效性：JaxMARL/SMAX，ALMA StarCraft multi-army 或 MAgent2 中至少跑通一个。**

HHMARL 2D 与用户的阶段式流程最相似，但仓库当前未显示明确许可证，只能阅读和 clean-room 重实现接口，不能直接复制/分发代码。

## 3. 为什么以 ALMA 为科学基础

ALMA 的公开代码已包含两个非常接近的环境：SaveTheCity 和 StarCraft multi-army，并提供 heuristic allocation、COPA 和 AQL allocator。它直接回答了“分层分配是否有必要”和“联合训练是否更好”，因此是高质量的顶会起点。

本文不应该简单给 ALMA 加一个注意力层，而应替换其上层价值接口：

~~~text
ALMA: state -> learned allocator Q -> task assignment -> low-level policy
本文: state + paired interventions -> calibrated outcome distribution
      -> robust two-sided allocation game -> same frozen low-level policy
~~~

若 ALMA 原始实验无法在三天内复现，保留其方法重实现和结果引用，但不要让旧 SC2 依赖阻塞主线。

## 4. 环境选择方案

### P0：当前 MultiFront-AD

在现有 SwarmBattle 上增加：

- 三个 Asset 实体及攻破/守住终局；
- assignment[agent_id] = (front_id, task_id)；
- 任务条件化的局部观测与奖励；
- clone_state() / restore_state() 与显式 RNG state；
- 最大槽位、active/dead/reinforcement mask；
- commander 每 \(H\) 步和事件触发接口。

P0 的目的不是直接投稿，而是在两周内回答：不同分兵是否真正改变关键点结果，以及简单 force-ratio 是否已经足够。

### 主实验：两种可行选择

**选择 A（推荐，工程连续性强）：**把 MultiFront-AD 做成公开 PettingZoo/VMAS 风格环境，进行全部 paired rollout；再在 ALMA SC2 multi-army 或 SMAX 上做固定人口外部验证。

**选择 B（吞吐优先）：**直接修改 SMAX，预分配最大单位槽位，用 active mask 模拟增援，并添加三个目标区域。JAX 便于从同一 state 批量展开候选和随机种子，但第一周改造风险更高。

第 1 周只允许二选一，不能同时重写 NumPy、PyTorch 和 JAX 三套环境。

## 5. 三天 upstream smoke gate

在独立、被 .gitignore 排除的外部目录中执行，不把第三方仓库直接提交进本项目：

1. 克隆 ALMA，记录 git rev-parse HEAD、许可证和 Docker 镜像摘要；
2. 先跑 SaveTheCity 最小 rollout，再测试 SC2 multi-army；
3. 只要求复现环境 reset/step、一个 heuristic 与一个 allocator 的短跑，不要求三天内重现论文曲线；
4. 失败时记录精确依赖/错误，转为 clean-room allocator baseline；
5. 同样为 JaxMARL 跑 SMAX reset/step 和短 MAPPO/QMIX smoke test。

由于本轮网络连接 GitHub CLI 失败，本仓库目前没有虚构 upstream SHA；正式拉取成功后再锁定 SHA，不能用“main 最新版”作为最终实验版本。

## 6. HHMARL 2D 的正确使用方式

可借鉴：先训局部技能、冻结后训 commander、宏微观不同频率、league/self-play 对手池。

不能直接照搬：

- 其 commander 主要选目标和 fight/escape，不是多线 coalition allocation；
- 观测维度与 N_OPPS_HL 等配置耦合，并非真正集合无关；
- 有战损但无局内增援、关键资产和双边 commander；
- 当前 GitHub 页面未见许可证，复制代码存在合规风险。

论文中使用名称 “HHMARL-style frozen commander”，由我们按论文描述独立实现，并在 artifacts 中公开差异。

## 7. 复现完成定义

一个 baseline 只有同时满足以下条件才算“复现”：

- 固定版本、依赖、随机种子和硬件记录；
- 在原作者最小场景上达到论文允许范围内的趋势或报告无法达到的原因；
- 迁移到本文环境时不改变其核心决策机制；
- 所有上层共享同一个下层 checkpoint、候选预算和观测；
- 训练步数、wall-clock 和超参数搜索预算等价；
- 未公开代码的方法附 clean-room 伪代码、单元测试和与论文公式的映射。

## 8. 推荐实现顺序

1. 现有 SwarmBattle 增加三资产与 assignment，脚本下层先隔离上层问题；
2. 生成同态势 paired rollout，先用 XGBoost / Logistic / Deep Sets 证明预测与选择信号；
3. 实现手工收益、Carion-style、Double-IC、oracle 与 COGAR structured solver；
4. 训练通用 MAPPO 下层并替换脚本；
5. 外部环境验证；
6. 最后才考虑 learned pointer commander 或阶段 4。
