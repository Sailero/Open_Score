## 0. 项目在做什么

这是一个**跨规模多智能体拦截**研究仓库。红方策略在小规模上训练，再放到更大人数、更多保护目标（以及二者同时变大）的测试配置上，看损伤会不会一起垮掉。

**HAD（主任务）**

- 红方拦截机 vs 规则控制的蓝方攻击机，保护 $K$ 个目标。
- 指标 $D$：目标累计损伤，越低越好。
- 训练：$N\in\{4,6,8,10\}$，$K\in\{1,2,3\}$，预算 1M 环境步。
- 终评：24 个配置 × 300 局，分成分布内（ID）、人数外推（N-OOD）、目标数外推（K-OOD）、联合外推。
- 正式比较只用达到预算的 **`final.pt`**。`best.pt` 是训练内验证选优档案，给自己复测、机制扫描用；存在权重文件不等于终评已经做完。

**SMACv2（确认任务）**

- 可变编制星际争霸微观操作，指标是胜率（越高越好）。
- 训练预算 5M 联合环境决策步；用来看 HAD 上的结构差别会不会在另一个可变规模任务上复现，不是主故事。

**当前主张口径（main0928）**

主方法是 **Looped、默认关掉 count 注入**（代码键 `regir_sg`，`skip_count_inject=True`）。它是 REFIL 宿主加上一条未锚定的循环关系旁路：实体之间先做多轮自注意力，再由个体 GRU 记忆去读这些带上下文的实体表征。唯一保留 count 的对照臂是 HAD 上的 `regir_count_sg`。

main0921 已经证明「关系模块整包相对 REFIL 有外推收益」，但没能证明「必须多轮、必须 count、必须共享参数循环」。main0928 把主方法收成无 count 的 Looped，用扁平矩阵做基线、消融和机制，不再走 main0923 的试训 / 分支闸门。

## 2. 软件框架

系统按四层组织。上层不知道 GPU 怎么分，下层不知道论文表怎么画。

### 2.1 环境层

| 模块 | 作用 | 完善度 |
|---|---|---|
| `open_score.envs.entity_env` / `had_wrapper` | HAD 实体接口：固定槽、死亡 mask、9 个平面动作、伤害回报 | 可用；协议冻结在 workbench 2.1 / r7 |
| `open_score.envs.smacv2_env` | SMACv2 可变编制适配；`SC2PATH` 指向克隆内或 `REGIR_ROOT` | 可用；依赖 SC2 4.10 与 protobuf 3.20.3 |
| `open_score.rules` | 红方整数规划拦截、蓝方 reactive/rush 等规则对手 | 可用；给 viewer 和锚点，不进学习矩阵 |
| `viewer.py` | 网页回放、自定义 checkpoint、比较队列 | 可用；结果只在会话内存，不写正式 CSV |

### 2.2 算法层

`open_score.algos.train(name, cfg)` 是统一训练入口。方法名在 `MAIN_OVERRIDES` 里展开成 PyMARL 配置。

| 族 | 代表键 | 作用 |
|---|---|---|
| 宿主基线 | `refil`、`b2_qmix_atten`、`dcg`、`alma`、`spectra`、`transfqmix` | 外部方法；HAD 权重从 main0921 导入，不重训 |
| Looped | `regir` / `regir_sg` | 未锚定循环关系 + REFIL 宿主 |
| 一阶对照 | `regir_r0_sg` | 同一模块只读原始实体 H0 |
| 单轮 | `regir_r1_sg` | 只有一轮（此时锚定与否等价） |
| 锚定循环 ARR | `regir_kv0_sg` | 每轮 K/V 固定为 H0 |
| 消融 | `norefil` / `nomem` / `last` / `fixed4` / `untied4` / `count` | 关宿主、关记忆、只读最后一轮、固定 4 轮、逐层解绑、打开 count |
| 稳定化 | `_sg` 后缀 | `global_query_detach_memory`：读出查询里截断记忆梯度 |

`best.pt` / `final.pt` / `resume.pt` / `config.json` 写在 `{output}/{method}/train/seed_N/`（SMAC 多一层 `smacv2/`）。`resume.pt` 只用于续训，不进正式表。

### 2.3 实验协议层

`open_score.eval.experiment` 冻结一场战役的身份：profile 名、种子、预算、训练表、机制表、导入基线、失败标准。它只提供数据，不拉起进程。

| Profile | 分支 | 流程 | 主方法 |
|---|---|---|---|
| `main0921` | `main0921` | 三种子正式矩阵，已冻结 | Full / 多方法并列 |
| `main0923` | `main` | 试训 → 分支闸门 → 公共 + 特有 | 候选 C/A/B（1-round / ARR / IAR） |
| `main0928` | `remote_train` | 扁平 P0/P1 矩阵，无闸门 | `regir_sg`（无 count） |

`protocol.py` 规定终评配置与 checkpoint 身份（`artifact_id` / `checkpoint_id`）。CSV 以身份去重，不用文件名，因为 `best.pt` 会被覆盖。

### 2.4 调度与执行层

两条队列进程读 JSON 队列，流水线进程写队列、刷新报告、画 status。

```
run_all.sh start|resume
        │
        ▼
open_score.eval.pipeline          每约 60s：盘点库存 → 写 queue.*.json → 拉起/重启子进程
        │
        ├── scripts/train.py      HAD / SMAC 训练队列（每卡占用、OOM 重试、resume.pt）
        └── scripts/eval.py       终评 / 机制 / 探针（可 CPU 或 GPU worker）
```

**本机 `main`（两张共享卡）**：`resources.py` 按显存自适应打包，GPU0/GPU1 有各自上限；HAD 与 SMAC 各有一个训练父进程。

**云端 `remote_train`（多机共享 NFS）**：`eval/cluster.py` 用 `os.mkdir` 抢 `cluster/claims/{task_id}/`，15 秒心跳、120 秒过期后别的机器从 `resume.pt` 续。每台机器 `nvidia-smi -L` 发现本地 GPU。主机名规范化成 `zN`。每机环境文件是 `envs/local.$HOST.env`，避免后启动的 setup 覆盖别人的 Python。

操作入口（云端）：

```bash
bash Open-SCORE/outputs/main0928/run_all.sh start|resume|stop|status|report|bundle|retry
```

`stop` 默认只停本机；全场用 `stop all`。已有战役必须用 **`resume`**，不要再用 `start`（`start` 会走准备流程，但不应被理解成「安全重入」）。

### 5.2 云端共享克隆上的现场补丁（还没有回到 git）

这些是训练打起来之后，直接改 TP 上那份代码、没有 `git pull`、也没有推回 GitHub 的部分。本机工作区**没有**这些文件的最终形态。要从农场拷回再提交。

1. **占用从「自适应打包」改成「每卡定路数」**  
   HAD 与 SMAC 共用一张卡的上限 `TRAIN_PER_GPU`。先锁 2，再因平台回收空闲卡改成 3，OOM 后又回到 2。GitHub 上的 `experiment.json` 模板仍是 HAD 每卡 3（可到 4）、SMAC 每卡 1（可到 2）的自适应描述。status 里看到的 `3/gpu` `8/12` 以**正在跑的进程加载的代码**为准，不是装饰。

2. **选卡与 claim**  
   遍历全部候选卡再选；释放本机占了但没真正开训的 claim；主机名 `sql-dream-zN--podhash` → `zN`；status 不再把各机 GPU 下标串台。

3. **NFS 日志锁**  
   多机同时写 `progress.csv` / `learning.csv` 时，`nfs_lock` 等 120 秒会 `TimeoutError` 直接杀掉训练，表现为 `retry regir_sg 0 (20 failed)`。现场改为这两类流 3 秒超时则**跳过该行**，训练继续。`task_failure.json` 里 count>2 仍会停排队，需要 `run_all.sh retry`。

4. **失败分类**  
   CUDA OOM 与锁超时分开。清过一批「锁超时 + 已有 `resume.pt`」的失败标记。之后剩下的耗尽任务几乎都是第三路挤进约 40GiB 卡导致的 OOM。

5. **`report0928` 学习曲线**  
   复用 0923 的 `_fig_learning` 时，HAD 面板方法列表是 FOUNDATION+CANDIDATES+IMPORTED，main0928 里 CANDIDATES 为空，所以只画出 R0。现场给 `render_figures` 加了包装，HAD 学习图改画 `TABLE2`。`fig2_scale` 仍可能走 0923 的旧方法列表。

6. **`bundle` 与 `.pending.png`**  
   出图原子写入 `.{stem}.pending.{ext}` 再 replace。打包先 `list` 再 `stat`，文件已改名就会 `FileNotFoundError`。权宜之计是排除 `*.pending*`。

7. **占用显示 vs 真并发**  
   卡上已经是 2 路时，只要加载的 cap 仍是 3，status 仍显示 `8/12`。这时 `retry` 会再塞进第 3 路，OOM 会回来。

### 5.3 本机 `main` 工作区未推送的 2 卡调度改动

这些文件改的是 **main0923 两张共享 GPU** 的打包器，不是 18 卡农场。不能 cherry-pick 进 `remote_train` 的 `experiment.py`（那边已经整文件换成 main0928 矩阵）。

涉及：`open_score/utils/resources.py`、`eval/experiment.py`、`eval/pipeline.py`、`scripts/train.py`、`scripts/eval.py`。

要点：

- GPU0 上 HAD+SMAC **合计**上限 `gpu0_total_trainers`（默认 3），用 `sibling_load` 看另一环境已经占了几路。
- 训练父进程按设备分片写 `scheduler.train.{env}.d{gpu}.json`，status / eval 用 `merge_train_scheduler` 合成；死 PID 丢掉。
- 队列锁改成 `gpu.{env}.d{devices}`，避免 HAD/SMAC 或按卡切开的父进程互相堵。
- `_job_is_busy`：锁或 `resource.json` 里还活着的 PID 已占着该 seed，就不要再入队。
- `gpu_admit` 允许某卡 cap=0；未测峰值只在该卡占用为 0 时开第一路；admission 对 SMAC 同样可读配置。
- 默认每卡从 2 调到 3（GPU1 仍可到 4）；status 压缩已完成分类行，给正在跑的训练留窗口。
- HAD 子进程 `--per-gpu` 2→3。

**没有**提交：`outputs/main0923/` 下重跑出来的 json/图/探针/权重（体积大、且是结果不是调度代码）。

### 5.4 运维结论（不是代码，但是本轮踩过的坑）

- 18×4090 分布：z1/z5 各 4，z2/z3/z4 各 2，z6 各 4。被平台回收后，常常只剩 z1+z5 还活着。
- 空闲或低利用率的卡会被回收，所以不能为了省显存把卡留空。
- 每卡 3 路 SMAC 会 OOM；2 路可以（例如 Looped s0 + SPECTra s0 同卡）。
- `zip` 命令在部分镜像里不存在，用 Python `zipfile` 或 `tar`。
- 活目录打包会 `file changed as we read it`：先快照再打包，或只打 CSV/图/权重。
- 分析文件与权重分开下。HAD 分析 + `best.pt` + `config.json` 大约几百 MB，全树十几 GB。
