# 价值论证与实际部署路径

**目的**：回答两个必须在立项阶段就锁死的问题——(1) 拟解决的问题是否确实有价值（谁在什么系统里疼）；(2) 这套方法是否**确确实实可以参与实际部署**（哪怕部署在虚拟环境/游戏中），而不是只活在自研 benchmark 里。
**结论先行**：问题价值可以落到三类真实系统的具体痛点上；方法的部署形态是"**零样本、免在线训练、CPU 可推理的实体列表→动作映射**"，接口契约与现有游戏引擎/服务器架构天然兼容；原型实测 64v64 全队决策延迟 12ms（CPU）/ 6ms（GPU），在任何主流 tick 预算内。

---

## 1. 拟解决问题的价值：三类真实系统的痛点映射

### 1.1 游戏 AI（最直接的部署场域，论文投稿后 3-6 个月可落地）

**痛点**：RTS/MOBA/自走棋/大逃杀类游戏的 NPC 团队 AI 至今以行为树+脚本为主，原因不是学习方法效果差，而是**部署条件苛刻**：
- 玩家阵容/数量每局都不同（匹配机制、中途掉线、召唤物），固定输入维度的策略网络直接不可用——这就是我们的**规模轴**；
- 玩家风格从"纯萌新"到"职业级"到"故意演AI的抽象打法"全谱系存在，对固定对手训练出的策略会被玩家迅速找到套路并利用——这就是我们的**对手轴**（exploiter 评测恰好模拟"玩家开发出针对性打法"）；
- 游戏运营方要求 AI 上线后**不能在线更新**（合规、回归测试成本），所以必须零样本泛化而非在线适应——恰好是我们协议的定义。

**双重零样本泛化 = 游戏团队 AI 的部署清单本身**。这不是类比，是同构。

### 1.2 大规模仿真推演/训练陪练系统

军民两用的仿真推演平台（含体育战术仿真、应急演练）需要"蓝方陪练 AI"：规模由演练想定随时改，风格要能模拟从保守到激进的谱系，且必须应对演练者的奇招。现状是每个想定人工配脚本，边际成本线性增长。一个规模无关+风格鲁棒的单一策略把边际成本降为零。

### 1.3 多机器人对抗性任务（长期）

无人机竞技（drone soccer/tag）、仓储机器人对抗性调度、安防巡逻对入侵者群。共同点：实体数量动态变化（故障退出=减员、补位=增援）、对手非合作。我们的点质量抽象与这些系统的上层决策层（导航目标分配）对齐——部署形态是"给每台机器人发目标点/目标对象"，正是模块 B 的输出语义。

### 1.4 反事实检验

若本工作不存在，上述系统的工程师只有三个选择：(a) 每个规模/风格配置单独训一个策略（组合爆炸）；(b) 平均场类方法（丢失小组战术结构，1.1-1.3 都需要结构化指令）；(c) 回到脚本。**这就是价值所在：我们提供第四个选择，且其部署契约（下节）比 (a)(b) 都简单。**

## 2. 部署契约（Deployment Contract）

方法对宿主系统的全部要求，以及宿主系统能得到什么。这一节的每一条都已被原型代码验证。

### 2.1 输入契约：实体列表（宿主侧零改造）

SAGA 的唯一输入是"当前可见实体的特征列表"（位置/速度/朝向/血量/阵营/类型属性，16 维/实体）。**所有游戏引擎与机器人中间件的世界状态天然就是实体列表**（Unity ECS、UE GameplayFramework、ROS tf tree、游戏服务器的 entity snapshot）。适配成本 = 写一个 ~100 行的特征提取器，我们已在三个异构环境上各写过一个（`prototype/envs/adapters.py`：SwarmArena/MPE/MAgent2），证明该契约的普适性。

### 2.2 时序契约：与 tick 架构对齐

- 微观策略每 tick 决策一次；指挥层每 k 个 tick 决策一次并广播目标向量——**与游戏服务器"高频物理 tick + 低频 AI tick"的标准架构完全同构**（如 30Hz 物理 + 4Hz AI）；
- 两次广播间单位只依赖局部观测（C3 约束），容忍通信丢包/延迟。

### 2.3 延迟契约：实测数据（RTX 3060 Laptop / i7 笔记本，torch 2.4，未做任何推理优化）

| 规模 | CPU 延迟 | GPU 延迟 | 参考预算 |
|---|---|---|---|
| 8v8 | 7.0 ms | 7.1 ms | MOBA/RTS AI tick 通常 100-250ms |
| 64v64 | 12.2 ms | 6.0 ms | 大逃杀服务器 tick ~50ms |
| 128v128 | 24.2 ms | 7.2 ms | |
| 256v256 | 65.0 ms | 12.4 ms | 仿真推演通常 ≥100ms/步 |

（`prototype/bench_latency.py` 可复现。）结论：**CPU 单核级推理即可上线到 128v128**，指挥层的 O(nd) 复杂度设计（而非 O(n²d) 自注意力）在这里兑现为部署价值。正式版转 ONNX/TorchScript 后还有 2-5 倍余量。

### 2.4 运维契约

- **免在线训练**：零样本泛化意味着上线后无梯度更新——无 A/B 回归风险、无在线数据合规问题（对游戏运营是硬要求）；
- **单一 checkpoint**：所有规模/风格共用一个 ~500KB-5MB 的参数文件（原型 111K 参数=463KB），版本管理与回滚成本极低；
- **可解释产物**：指挥层的簇分配与任务分配是显式的中间量，可直接渲染为调试 UI（我们的 HTML 回放器就是雏形）——运营方可审计"AI 为什么这么打"，这是黑盒扁平策略做不到的；
- **降级路径**：任一模块异常时可无缝退回脚本库（脚本库本来就是训练资产的一部分）。

### 2.5 部署风险的诚实清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 训练环境与宿主物理差异（sim2sim gap） | 微观机动策略可能失真 | 部署形态优先取"指挥层输出目标 + 宿主原生寻路执行"的半接入模式（只部署模块 A+B），微观层由宿主引擎接管 |
| 宿主实体特征与训练 schema 不齐 | 属性向量分布漂移 | §5.5 属性外推实验直接量化该敏感度；特征提取器做标准化对齐 |
| 极端规模（>256） | 延迟超预算 | 指挥层降频 + 敌实体先做粗聚类降采样（O(nd) 里的 n 可控） |

## 3. 部署路线（与论文时间线解耦，投稿后执行）

**Tier 0（随论文发布）**：SwarmArena + 回放器 + 预训练 checkpoint 开源；提供"对战 API"（HTTP/gRPC 输入实体列表返回动作），社区可接入任意脚本挑战——这本身就是一次虚拟环境部署。

**Tier 1（+1-3 个月，公开对战平台）**：接入现成的公开游戏 AI 竞技场，用真实第三方对手检验对手轴泛化：
- **microRTS 竞赛**（单位数量可变、完全对抗、年度锦标赛、纯 Java/Python 接口）——与我们场景同构度最高；
- **Lux AI（Kaggle）**：双方单位数动态增减（正好是增援/减员语义）、公开天梯、对手谱系=全球参赛者；
- **SC2 AI Arena 天梯**（python-sc2 bot）：社区 bot 风格极多样，是"未见对手"的天然测试场。
选其一做成 workshop/demo 论文的续作，同时为主论文提供"真实部署"的 camera-ready 补充材料。

**Tier 2（+6 个月，产业接口）**：半接入模式 SDK（模块 A+B 出目标，宿主执行）+ Unity/UE 示例工程，目标客户为游戏工作室 NPC 团队 AI 与仿真推演供应商。
