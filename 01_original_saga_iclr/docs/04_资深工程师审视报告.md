**评审视角**：假设我是一位做过多篇 MARL 顶会论文、带过工程团队的资深研究工程师，对本仓库的全部代码与文档做一次不留情面的 review。

**结论先行**：**方向可行、价值真实、但当前距离 ICLR 可投稿状态还有约 70% 的工作量**。研究设计（问题聚焦、贡献结构、评测协议）已达到 ICLR 论文的骨架水准；原型代码验证了接口正确性但**没有验证任何科学主张**；最大的三个风险是训练基础设施、动态分簇的可学习性、以及基线对比的公平性。

## 1. 可行性评估（逐模块）

### 1.1 环境与接口层 —— ✅ 可行，质量合格

`swarmbattle/env.py` + `envs/adapters.py` 的设计是对的：

- 实体 token 接口（16 维统一布局）与三个环境（SwarmBattle / MPE / MAgent2）的适配已跑通，这证明了"同一网络跨环境复用"的工程可行性——这是论文回应"自研环境"质疑的关键证据链，**已成立**；
- 变规模、中途增援、属性化异构的机制都在环境中实现且被冒烟测试覆盖。

**但有三个必须修的问题**：

1. **NumPy 逐单位循环的性能天花板**。`_observations()` 对每个存活单位做一次 `_entity_tokens`，是 O(N²) 的 Python 循环。64v64 时单步观测构建就要 ~128 次全队距离计算。论文需要 10⁹ 步级别的采样，**当前实现每秒最多几千步，差 3-4 个数量级**。必须迁移 JAX（原计划 W1-2 就是这个）或至少全向量化 NumPy。
2. **MAgent2 适配器的语义妥协**。红方名单与网格位置的对应是"近似"的（按顺序对齐），蓝方脚本的移动是随机 bin——这在 demo 级别可接受，但如果 MAgent2 要作为论文的正式评测环境，必须改用 per-agent 观测（`obs` 自带 13×13×5 局部视野）而非从全局 state 网格反推实体，否则审稿人复现时会发现行为不一致。
3. **SwarmBattle 缺少碰撞与视线遮挡**。当前单位可以互相穿透，"包抄"等战术的物理意义打折。至少加一个软碰撞惩罚，否则涌现行为分析（论文主图 4）说服力不足。

### 1.2 SAGA 网络（模块 A/B/C）—— ✅ 架构可行，⚠️ 可学习性未验证

- 模块 A（SAQA 交叉注意力）和模块 C（目标打分式开火头）是成熟做法的正确组合，参数量 111K 与数量解耦已验证，**低风险**；
- 模块 B 是全文最大的创新点也是最大的**未验证风险**。当前 demo 里 `active_clusters` 恒等于 6（=K_max）——这说明 slot attention 的 occupancy 并没有像设计声明的那样"空 slot 自动退化"。冒烟测试只验证了张量形状，没有验证聚类行为。**这是最高优先级的科学风险**：如果软聚类学不出对齐敌方结构的簇，Claim 2 直接塌掉。
  - 已有的对冲方案（Sinkhorn 分配 / DBSCAN 预训练）写在 `03_预期结果与风险.md` 里，但**没有任何一个被实现**。审慎的做法是：下一步先做一个"聚类行为单元测试"——构造敌方明显分两群的合成态势，检查 occupancy 是否收敛到 2 个有效簇。这个实验一天能做完，能提前两个月暴露风险。
- `z_opp` 风格编码器目前吃的是随手拼的 8 维统计量（`team_stats`），其中第 8 维恒为 1.0，纯属占位。正式版需要精心设计交战统计量（开火频率、压上速度、重组频率等），并做 t-SNE 验证可分性。

### 1.3 训练器 —— ❌ 当前实现不可用于正式实验

`train_demo.py` 的 PPO 是**逐 transition 前向的 Python 循环**（`ppo_update` 里 `for i in batch` 每个样本单独 forward）。这是 demo 里训练慢（10 秒/局）的根源，GPU 利用率可能不足 5%。正式实验必须重写：

- 按"episode 内单位数相同"的批次做 padding + batched forward；
- 或直接在 JAX 里重写（推荐，与环境迁移合并做）。

另外三个训练科学问题：

1. **120 局的 demo 曲线不能说明任何事**。回报 -7.9→-5.5 的改善幅度与方差同量级（曲线上尖峰是 ±7 的单局波动），且胜率 5-10% 主要来自超时判定而非歼灭。**不要在任何对外材料里把这条曲线当"方法有效"的证据**，它只证明"流水线无 bug"。
2. **信用分配缺失**：队级团队奖励 + 队级 value（`unit_emb.mean` 池化）在 N 变大时会遇到严重的 lazy agent 问题。方案文档里说"任务达成塑形"，但代码里完全没有实现。这是正式版必须补的（每单位的任务对齐奖励 → 需要 commander 的 assign 矩阵参与奖励计算）。
3. **自博弈/种群课程 0% 实现**。目前只有固定脚本对手。SxS 课程、快照池、exploiter 流水线全部还是纸面设计。这是工作量最大的一块（估 3 周）。

### 1.4 GPU/平台 —— ⚠️ 本机不够，需要尽早解决

RTX 3060 Laptop 出现过 CUDA unknown error（TDR 嫌疑），且显存/算力对 10⁹ 步训练完全不够。**行动项：立即申请/确认实验室服务器或云 GPU（至少 1×A100 或 4×3090），并在 WSL2/Linux 上把 JAX 环境搭起来**。这是排期上的关键路径，不是技术风险而是资源风险。

## 2. 价值评估 —— ✅ 真实且时机好

重新压力测试一遍核心主张，我认为立得住：

1. **"双重零样本泛化（规模 × 对手）"的问题框架有独立价值**。我检索过的所有近邻（MF-MAPPO、SPECTra、AHDRL_LRS、OEOM）都只覆盖单轴。把两轴统一成一个评测协议 + 指出"两者是同一表征问题的两面"，这是 ICLR 喜欢的抽象层级。
2. **"对手锚定动态分簇"有清晰的可证伪机制**：簇数与语义由敌方实时结构决定。这不是"加个注意力"式的增量——固定 K 分组基线与它的对比是一个干净的科学实验。
3. **反事实检验**：如果这篇论文不存在，社区缺什么？缺一个证明"分组结构应该锚定对手而非预设"的证据，缺一个"episode 内增减员"的评测协议。两者都是真空白。

**价值方面唯一的担忧**：军事色彩。ICLR 审稿人中有相当比例对 battlefield 应用敏感。**建议论文叙事全面改用中性术语**（pursuit-evasion / adversarial swarm games / attrition games），环境命名避免 battle 字眼（可改叫 SwarmArena），并在 Ethics Statement 里主动讨论 dual-use。这不是可选项，是录用概率的实质变量。

## 5. 对论文写作的指导意见（本次同步执行）

1. **立即开始写论文而不是等实验**——Introduction/Related Work/Problem Formulation/Method 不依赖实验数据，现在写完可以反向锁定实验必须产出什么图表（我在 `paper/05_experiments.md` 里用"图表合同"的形式写死）。
2. **贡献声明要收敛到 3 条**（问题+协议 / 架构 / 课程），抵制把每个模块都列成贡献的诱惑。
3. 术语中性化从论文第一稿就执行，避免后期全文替换出错。
4. 每章一个独立 md 文件（便于版本管理与并行修改），最终由脚本拼接转 LaTeX。

论文草稿见 `paper/` 文件夹，各章节状态见 `paper/README.md`。
